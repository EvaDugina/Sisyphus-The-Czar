## Функциональные требования

- **Восстановление конфигурации Сцены 1:** Система должна вернуть настройки Git-шаблона Сцены 1 к состоянию до тестовой перезаписи, сохранив схему настроек 61 и параметр `preclickPopupOnAnySceneClickEnabled`.
  - **Пояснение:** Тестовый запуск не должен становиться источником production/demo-конфигурации.
  - **Источник:** «ИСПРАВЬ».
  - **Acceptance hint:** Diff шаблона Сцены 1 относительно исходного состояния содержит только осознанную миграцию схемы и новый параметр.

- **Создание версии при новом имени:** Если пользователь изменил имя выбранной версии и сохраняет настройки, система должна создать новую версию с новым ID, не изменяя исходную версию.
  - **Пояснение:** Новое имя означает новый именованный снимок, а не скрытое переименование и замену существующего шаблона.
  - **Источник:** «чтобы больше никогда».
  - **Acceptance hint:** После сохранения под новым именем в каталоге присутствуют обе версии с разными ID, исходная версия и её настройки не изменены.

- **Обновление существующей версии без переименования:** Если имя выбранной версии не менялось, сохранение должно обновлять эту версию по существующему ID с действующей защитой от конфликтов.
  - **Пояснение:** Исправление не должно ломать штатное редактирование существующего снимка.
  - **Источник:** Одобренный черновик требований.
  - **Acceptance hint:** Сохранение с прежним именем обновляет существующую запись без создания дубля.

- **Изоляция сохраняющих smoke-тестов:** Smoke-тесты, проверяющие сохранение шаблонов, должны работать с отдельным временным settings-template store и не иметь возможности записывать в рабочий `config/settings-templates.json`.
  - **Пояснение:** Проверка реального серверного API остаётся полноценной, но её данные одноразовые.
  - **Источник:** «чтобы больше никогда».
  - **Acceptance hint:** После smoke-прогона рабочий конфигурационный файл побайтно не изменён, а тестовые версии отсутствуют в нём.

## Нефункциональные требования

- **Защита отслеживаемой конфигурации:** Автоматические тесты не должны изменять отслеживаемые Git-конфигурации или зависеть от уже запущенного dev-сервера с рабочим хранилищем.
  - **Пояснение:** Повторный прогон тестов должен быть детерминированным и безопасным для рабочей копии.
  - **Источник:** «чтобы больше никогда».
  - **Acceptance hint:** Тестовый сервер получает явно заданный временный путь хранения, очищаемый после прогона.

- **Регрессионная защита:** Автоматические проверки должны покрывать создание новой версии при переименовании, обновление без переименования и изоляцию рабочего файла.
  - **Пояснение:** Оба механизма, которые привели к повреждению, должны контролироваться тестами.
  - **Источник:** Одобренный черновик требований.
  - **Acceptance hint:** Релевантные unit/smoke-тесты падают при возврате прежнего поведения.

- **Совместимость:** Исправление не должно менять синхронизацию параметров между браузерами и игровую механику сцен.
  - **Пояснение:** Зона изменения ограничена версиями настроек и тестовой инфраструктурой.
  - **Источник:** Одобренный черновик требований.
  - **Acceptance hint:** Действующие проверки настроек и основного сценария остаются зелёными.

## Проблемы и замечания, превращённые в требования

- **Тест перезаписывает рабочий шаблон:** Сейчас smoke-тест отправляет сохранение в реальный dev-сервер, который пишет в рабочий `config/settings-templates.json`. Требуемое поведение: тест использует только временное хранилище и не оставляет изменений в репозитории.
  - **Источник:** «конфигурация не сохранилась (сохранилась неверно)» и «чтобы больше никогда».
  - **Acceptance hint:** До и после smoke-прогона содержимое рабочего файла идентично.

- **Новое имя переиспользует ID базовой версии:** Сейчас UI выбирает базовую версию для сохранения даже после изменения имени, поэтому сервер штатно заменяет существующую запись полным текущим снимком. Требуемое поведение: изменение имени отделяет новый снимок от базовой версии и выдаёт ему новый ID.
  - **Источник:** «сохранилась неверно».
  - **Acceptance hint:** Исходный ID и запись остаются неизменными, новый снимок получает отдельный ID.
