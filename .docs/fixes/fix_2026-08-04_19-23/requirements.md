## Контекст

- Нижняя точка подъёма считается высотой `0vh`.
- Высота препятствия задаётся в `vh`; для исходной сцены `10000vh` зона 10–15% равна `1000–1500vh`.
- «Окна» — реальные отдельные окна браузера через `window.open()`, а не внутриигровые панели.
- Современный браузер может блокировать автоматические popup-вызовы без отдельного пользовательского действия. Система не обходит это ограничение.

## Функциональные требования

- Категория настроек «Руки» переименовывается в «Рука» (`РУКА` при верхнем регистре).
- В UI появляется категория «Препятствия» с первой группой «Окна» и переключателем активности.
- Для «Окон» доступны «Высота от» и «Высота до» с шагом `100vh`; значения по умолчанию `1000vh` и `1500vh`.
- Новые окна генерируются, пока центр камня находится внутри включительно заданного диапазона высоты от нижней стартовой точки.
- Минимальный/максимальный интервал: по умолчанию `0,5–1,5 с`, диапазон `0,1–30 с`, шаг `0,1 с`.
- После каждого успешно открытого окна следующий интервал заново выбирается случайно в настроенном диапазоне.
- Минимальная/максимальная ширина: по умолчанию `240–640 px`, диапазон `100–1920 px`, шаг `10 px`.
- Минимальная/максимальная высота: по умолчанию `160–480 px`, диапазон `100–1080 px`, шаг `10 px`.
- Ширина и высота каждого окна выбираются независимо и ограничиваются доступной рабочей областью конкретного экрана.
- Окно пустое, закрывается кликом внутри либо автоматически через 2 секунды.
- Несколько окон могут существовать одновременно; закрытие одного не закрывает остальные.
- Пока открыто хотя бы одно окно-препятствие, захват и управление камнем в основном окне заблокированы, но физическая симуляция продолжается.
- После выхода камня из диапазона будущий timer отменяется, уже открытые окна продолжают обычный lifecycle. При повторном входе планируется новый случайный интервал.
- Нижние границы диапазонов высоты, интервала и размеров не могут превышать верхние.
- Настройки сохраняются, загружаются и мигрируют вместе с остальными настройками сцены.
- В группе «Окна» отображается статус popup-разрешения и действие для открытия тестового окна.
- Состояния разрешения: «не проверено», «тест открыт», «разрешено», «заблокировано».
- Если popup заблокирован, попытка не считается успешным показом, автоматическая генерация приостанавливается, UI объясняет необходимость разрешить всплывающие окна.
- Поведение и настройки совпадают на `/` и `/drafts/`.

## Нефункциональные требования

- Изменение настроек, reconnect и повторный вход в диапазон не создают дублирующихся timer.
- Блокировка управления снимается только после закрытия последнего активного окна.
- Закрытые пользователем popup обнаруживаются независимо от двухсекундного автозакрытия.
- При dispose/reload все timer очищаются, а принадлежащие текущему runtime окна закрываются.
- `config/settings-templates.json` в этой итерации не изменяется.

## Ограничения

- Автоматическое открытие надёжно работает только после разрешения popup для origin.
- Система не заменяет popup внутриигровой имитацией и не обходит popup-блокировщик.
- Не реализуются другие препятствия, столкновения окна с камнем, содержимое, перетаскивание и настройка времени жизни.

## План реализации

1. Добавить версионируемые room settings и нормализацию пар `min/max`.
2. Добавить UI категорий «Рука» и «Препятствия / Окна» со статусом и тестом popup.
3. Вынести lifecycle в отдельный контроллер препятствия окон.
4. Связать активные окна с блокировкой grab без остановки physics loop.
5. Покрыть нормализацию, расписание, popup-blocked и independent-close тестами.
6. Обновить `.docs/*`, проверить `/` и `/drafts/` в Docker dev-среде.
