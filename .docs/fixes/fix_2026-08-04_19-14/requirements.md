## Исходный текст

Пользователь попросил переименовать категорию настроек «Руки» в «Рука» и добавить препятствия, размещаемые на разных высотах страницы. Для первой категории препятствий «Окна» согласованы отдельные браузерные окна: они активируются в диапазоне высоты от нижней точки подъёма, появляются через случайные интервалы, имеют случайные настраиваемые размеры, могут существовать одновременно, блокируют управление камнем и закрываются по клику внутри окна либо автоматически через 2 секунды.

Высота задаётся в `vh` с шагом `100vh`; для первого препятствия начальный диапазон — `1000–1500vh`. Числовые значения интервалов и размеров разрешено выбрать при реализации и затем донастроить через UI.

## Функциональные требования

- **Переименование категории:** Система должна отображать категорию настроек «Руки» как «Рука»; при визуальном преобразовании в верхний регистр — «РУКА».
  - **Пояснение:** В игровой модели существует единственная рука.
  - **Источник:** «Измени на UI категорию: не РУКИ а РУКА».
  - **Acceptance hint:** В панели настроек присутствует категория «Рука», а категория «Руки» отсутствует.

- **Категория препятствий:** Система должна добавить на UI категорию «Препятствия» с первой и пока единственной группой «Окна».
  - **Пояснение:** Другие типы препятствий в эту итерацию не входят.
  - **Источник:** «Пока только первая категория препятствий \"Окна\"».
  - **Acceptance hint:** На `/` и `/drafts/` доступна категория «Препятствия» с группой «Окна».

- **Включение препятствия:** Группа «Окна» должна содержать переключатель активности.
  - **Пояснение:** При выключенном переключателе новые окна не создаются.
  - **Источник:** Требование предоставить управление препятствием на UI.
  - **Acceptance hint:** Выключение настройки останавливает планирование новых окон.

- **Координата высоты:** Система должна измерять высоту препятствия от нижней точки подъёма, принимая её за `0vh`, и изменять границы с шагом `100vh`.
  - **Пояснение:** Высота задаётся абсолютными значениями `vh`, а не процентами страницы.
  - **Источник:** «0 находится в нижней точке. Задавай высоту не в % а в vh, деления по 100 vh».
  - **Acceptance hint:** Значения высоты кратны `100vh`, а увеличение значения перемещает диапазон вверх от старта.

- **Диапазон активации:** UI должен содержать настройки «Высота от» и «Высота до» со значениями по умолчанию `1000vh` и `1500vh`.
  - **Пояснение:** Генерация окон работает, пока центр камня находится внутри включительного диапазона.
  - **Источник:** Первоначальный диапазон 10–15% и последующее уточнение единиц `vh` для сцены `10000vh`.
  - **Acceptance hint:** Вне диапазона новые окна не открываются; при входе в диапазон запускается новый случайный интервал.

- **Интервал появления:** UI должен позволять задавать минимальный и максимальный интервал в пределах `0,1–30 секунд` с шагом `0,1 секунды`; значения по умолчанию — `0,5–1,5 секунды`.
  - **Пояснение:** После каждого успешно открытого окна следующая задержка заново выбирается случайно в настроенном диапазоне.
  - **Источник:** «После каждого показанного окна время следующего показа окна рассчитывается рандомно в указанном диапазоне» и «Выбери любые, я донастрою».
  - **Acceptance hint:** Последовательные задержки находятся между минимумом и максимумом и пересчитываются после каждого успешного открытия.

- **Настройка размеров:** UI должен позволять задавать минимальную и максимальную ширину и высоту окна в пикселях.
  - **Пояснение:** Ширина по умолчанию — `240–640px`, высота — `160–480px`; допустимая ширина — `100–1920px`, допустимая высота — `100–1080px`, шаг — `10px`.
  - **Источник:** «Нужно» на вопрос о настройке минимального и максимального размера.
  - **Acceptance hint:** Размер каждого окна случайно и независимо выбирается внутри настроенных диапазонов и ограничивается доступной областью экрана.

- **Отдельные браузерные окна:** Система должна создавать препятствия через отдельные браузерные popup-окна, а не через внутриигровые панели.
  - **Пояснение:** Окно остаётся пустым и закрывается по клику в любой его внутренней области.
  - **Источник:** «Отдельные окна» и «Окно закрывается либо по клику внутри окна, либо через 2 секунды».
  - **Acceptance hint:** Успешное событие создаёт новый browsing context, а клик внутри закрывает только выбранное окно.

- **Автозакрытие:** Каждое успешно открытое окно должно автоматически закрываться через 2 секунды, если пользователь не закрыл его раньше.
  - **Пояснение:** Таймеры жизненного цикла независимы для каждого окна.
  - **Источник:** «Окно закрывается либо по клику внутри окна, либо через 2 секунды».
  - **Acceptance hint:** Окно исчезает не позднее чем через 2 секунды после открытия.

- **Одновременные окна:** Система должна разрешать открытие нового окна до закрытия ранее открытых.
  - **Пояснение:** Закрытие одного окна не влияет на остальные.
  - **Источник:** «Могут» на вопрос об одновременном отображении нескольких окон.
  - **Acceptance hint:** При интервале меньше 2 секунд одновременно наблюдаются несколько независимых окон.

- **Блокировка управления:** Пока открыто хотя бы одно окно-препятствие, система должна блокировать пользовательское управление камнем в основном окне, не останавливая физическую симуляцию.
  - **Пояснение:** Управление возобновляется после закрытия последнего активного окна.
  - **Источник:** «Окна должны перекрывать управление».
  - **Acceptance hint:** Ввод не двигает и не захватывает камень при активном окне, но симуляция продолжает обновляться.

- **Выход и повторный вход в диапазон:** После выхода камня из диапазона система не должна создавать новые окна; уже открытые закрываются по обычным правилам. При повторном входе запускается новая случайная задержка.
  - **Пояснение:** Расписание привязано к текущей высоте камня.
  - **Источник:** Требование размещать препятствие на определённой высоте.
  - **Acceptance hint:** Вне диапазона число новых popup-окон не растёт.

- **Валидация и сохранение:** Система должна запрещать значения, где минимум больше максимума, и сохранять настройки препятствия вместе с остальными настройками сцены.
  - **Пояснение:** Настройки должны проходить существующую нормализацию, миграцию и восстановление.
  - **Источник:** Требование предоставить все диапазоны на UI.
  - **Acceptance hint:** Некорректные входные данные нормализуются, а корректные восстанавливаются после перезагрузки.

- **Обработка popup-блокировщика:** UI должен показывать статус разрешения, предоставлять действие для проверки тестового окна и приостанавливать генерацию при блокировке.
  - **Пояснение:** При блокировке система объясняет необходимость разрешить popup-окна для сайта; внутриигровая подмена не используется, а заблокированная попытка не считается успешным показом.
  - **Источник:** Техническое ограничение согласованного механизма отдельных браузерных окон.
  - **Acceptance hint:** Возврат `null` из `window.open()` переводит препятствие в состояние «заблокировано» без повторного частого открытия.

## Нефункциональные требования

- **Надёжность таймеров:** Система не должна создавать дублирующиеся планировщики после изменения настроек, переподключения или повторного входа в диапазон.
  - **Пояснение:** Для каждой клиентской сессии действует один планировщик открытия, а у каждого окна — собственный таймер закрытия.
  - **Источник:** Требование повторяющихся случайных показов и поддержки нескольких окон.
  - **Acceptance hint:** Повторное включение и вход в диапазон не умножают частоту событий.

- **Совместимость размеров:** Система должна ограничивать запрошенные размеры доступной рабочей областью экрана.
  - **Пояснение:** Браузер и ОС могут дополнительно корректировать размер popup-окна.
  - **Источник:** Требование произвольных настраиваемых размеров.
  - **Acceptance hint:** Ни один рассчитанный размер не превышает доступную область экрана.

- **Паритет интерфейсов:** Настройки и поведение должны совпадать на основной странице `/` и `/drafts/`.
  - **Пояснение:** Обе страницы используют общий runtime и конфигурацию.
  - **Источник:** Существующий контракт проекта для основного и draft-интерфейсов.
  - **Acceptance hint:** Smoke-тест на обеих страницах находит одинаковые контролы и значения.

- **Зависимость от разрешения браузера:** Автоматические отдельные окна должны считаться доступными только после разрешения popup-окон пользователем в браузере.
  - **Пояснение:** Современные браузеры ограничивают `window.open()` без непосредственного пользовательского действия; приложение не может программно обойти это ограничение.
  - **Источник:** Ограничение Web API `Window.open()`.
  - **Acceptance hint:** При запрете UI сообщает о блокировке и не создаёт бесконечный цикл попыток.

## Проблемы и замечания, превращённые в требования

- **Несогласованное название:** Сейчас категория «Руки» не соответствует модели с единственной рукой. Требуемое поведение: категория называется «Рука».
  - **Источник:** «не РУКИ а РУКА».
  - **Acceptance hint:** В UI отсутствует заголовок «Руки».

- **Отсутствие препятствий:** Сейчас приложение не умеет активировать препятствия по высоте подъёма. Требуемое поведение: категория «Препятствия» управляет первым типом «Окна» в диапазоне `vh` от нижней точки.
  - **Источник:** «Добавь на UI на разных высотах возможность расставлять разные препятствия».
  - **Acceptance hint:** В заданном диапазоне камня и при разрешённых popup-окнах открываются отдельные окна.

## Не включено / требует уточнения

- Другие типы препятствий.
- Физические столкновения окон с камнем.
- Внутриигровая имитация popup-окон.
- Перетаскивание или содержимое окон.
- Настройка фиксированного времени жизни окна в 2 секунды.
- Программный обход popup-блокировщика.
